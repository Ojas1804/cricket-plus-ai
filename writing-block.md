## Product Requirements Document (PRD) & System Architecture

**Version:** 1.0  
**Status:** Approved architecture baseline  
**Date:** November 2026  
**Product type:** AI-powered cricket analytics workspace  
**Deployment:** Local, Docker Compose  
**Primary audience:** Cricket enthusiasts, analysts and statisticians

# 1. Product Overview

## 1.1 Vision

Cricket Canvas is a dynamic, AI-powered cricket information and analytics platform where users can retrieve, analyse and visualize any cricket-related information through natural-language prompts.

Unlike traditional cricket websites, Cricket Canvas will not rely on predefined pages for individual players, teams, competitions or statistics.

Instead, users interact with a common workspace. They submit prompts, and the application dynamically constructs appropriate visual components based on the requested information.

Examples:

- Show the top 10 run scorers in IPL history.
- Compare Virat Kohli and Steve Smith in Test cricket over the last 10 years.
- Show India's performance against Australia in Australian conditions.
- Display all currently running international matches.
- Analyse the bowling performance of Jasprit Bumrah against left-handed batsmen.
- Show the evolution of batting strike rates in T20 cricket.
- Compare the performance of two teams across different venues.

The application should determine the appropriate representation for each request, including tables, charts, scorecards, player profiles, images, statistical summaries and interactive visualizations.

## 1.2 Core product philosophy

1. Prompt-first, not page-first.
2. Every prompt creates an independent widget by default.
3. Existing widgets remain untouched unless the user explicitly requests an update or removal.
4. Widgets are movable and independently interactive.
5. Different widgets can communicate through shared cricket entities.
6. Statistical calculations are performed by deterministic application logic, not generated by the LLM.
7. Every statistical result should be traceable to its underlying data and filters.
8. The system should support adding new visualization types without redesigning the application.

## 1.3 Target audience

Primary:

- Cricket enthusiasts interested in detailed statistics.
- Cricket analysts and researchers.
- Users interested in player and team comparisons.
- Users exploring historical and live cricket data.

The interface should support both simple queries and complex analytical requests without requiring users to understand SQL or cricket database schemas.

# 3. User Experience Requirements

## 3.1 Homepage

The homepage will consist of:

1. Application header.
2. Central prompt input.
3. Suggested prompts.
4. Dynamic widget workspace.

The homepage should not contain a conventional navigation menu for individual players, teams or tournaments.

### Prompt interface

Users should be able to submit natural-language queries.

Suggested prompt categories:

- Live cricket.
- Player statistics.
- Player comparisons.
- Team statistics.
- Tournament statistics.
- Historical analysis.
- Advanced analytics.

Suggested prompts should be dynamically configurable in the future.

## 3.2 Prompt submission behavior

There will be two primary operations.

**Add new widget**

Creates a new widget or collection of widgets in the existing workspace.

This is the default operation.

**Update existing widget**

Modifies a selected widget using a new prompt.

The following properties must be preserved when updating a widget:

- Widget ID.
- Dashboard position.
- User-defined dimensions.
- Expanded or collapsed state, where applicable.
- Existing interaction relationships when still relevant.

Updating one widget must not affect unrelated widgets.

### Example

Initial prompt:

"Show the top 10 IPL run scorers."

Result: A leaderboard widget.

Follow-up:

"Only show players who have played at least 50 matches."

Result: Update the existing leaderboard.

New prompt:

"Compare Virat Kohli and Rohit Sharma."

Result: Create an additional comparison widget.

## 3.3 Workspace behavior

The dashboard will use a responsive grid layout.

Requirements:

- Drag-and-drop widgets.
- Automatic repositioning.
- Independent widget refresh.
- Expand and collapse.
- Widget removal.
- Widget duplication.
- Widget-specific query editing.
- Selective resizing.
- Automatic text-widget height.
- Responsive layouts.

Resizing should be enabled for tables, charts, scorecards and images. Text widgets should normally use automatic sizing.

A widget should have a drag handle separate from its interactive content.

## 3.4 Widget header

Each widget should have:

- Title.
- Data source indicator.
- Last updated timestamp.
- Drag handle.
- Refresh control.
- Expand/collapse control.
- Context menu.

Context menu actions:

- Edit query.
- Update widget.
- Duplicate.
- Refresh.
- Export.
- Remove.

## 3.5 Error handling

Widgets should fail independently.

For example, if the live-score provider becomes unavailable, historical statistics widgets should continue functioning.

A failed widget should display:

- What failed.
- Whether the data is stale.
- Last successful update.
- Retry option.

The entire dashboard must never fail because one widget encounters an error.

The backend will return a validated widget specification.

Example:

```json
{
  "schemaVersion": "1.0",
  "id": "widget-123",
  "type": "leaderboard",
  "title": "Top IPL Run Scorers",
  "description": "Highest career run totals in IPL",
  "query": {
    "competition": "IPL",
    "metric": "runs",
    "sort": "descending",
    "limit": 10
  },
  "data": {
    "columns": ["rank", "player", "runs"],
    "rows": []
  },
  "metadata": {
    "source": "internal_analytics",
    "lastUpdated": "2026-11-16T10:00:00Z",
    "filters": {},
    "coverage": {}
  },
  "interactions": {
    "selectableRows": true,
    "linkedEntity": "player"
  }
}
```

This is an illustrative contract. Production schemas should be defined using Pydantic models and TypeScript interfaces.

## 4.3 Widget lifecycle

Supported states:

- CREATED
- PLANNING
- FETCHING
- COMPUTING
- RENDERING
- READY
- REFRESHING
- ERROR

Widgets should support asynchronous loading.

A long-running analytical query should not block the entire dashboard.

## 4.4 Multiple-widget responses

One user prompt may generate multiple widgets.

For example:

"Compare Virat Kohli and Rohit Sharma and show their performance trends in IPL."

This could generate:

1. Comparison widget.
2. Career statistics table.
3. Performance trend chart.

The backend should return a collection of widget specifications associated with the same prompt execution.

Each widget must have its own stable ID.

# 5. AI Orchestration Architecture

## 5.1 Core principle

The LLM is responsible for understanding user intent and planning the required operations.

It is not responsible for calculating cricket statistics or generating executable frontend code.

The application will use a multi-stage orchestration pipeline.

## 5.2 Processing pipeline

### Stage 1: Intent extraction

Extract:

- Cricket entities.
- Players.
- Teams.
- Competitions.
- Formats.
- Time ranges.
- Venues.
- Statistical metrics.
- Filters.
- Sorting.
- Limits.
- Requested visualizations.
- References to existing widgets.

### Stage 2: Entity resolution

Resolve user-provided names to canonical database identifiers.

Examples:

- Virat Kohli → player ID.
- India → team ID.
- IPL → competition ID.
- MCG → venue ID.

Handle aliases, spelling differences and ambiguous names.

If multiple players match, ask the user for clarification.

### Stage 3: Query planning

Convert the request into an executable analytical plan.

Example:

User request:

"Compare Indian batting against Australia in Australia since 2015."

Plan:

1. Retrieve Test matches.
2. Filter matches involving India and Australia.
3. Filter venues located in Australia.
4. Filter match dates from 2015 onwards.
5. Retrieve Indian batting performances.
6. Aggregate runs, dismissals, averages and strike rates.
7. Calculate player-level metrics.
8. Return structured datasets.

### Stage 4: Data-source selection

Select the appropriate source based on the query.

Examples:

- Historical statistics → PostgreSQL analytics.
- Ball-by-ball analysis → Delivery-level database.
- Live scores → Live cricket provider.
- Player images → Image provider.
- Upcoming fixtures → Fixture provider.

### Stage 5: Analytics execution

Execute validated operations through approved analytics functions.

No arbitrary LLM-generated SQL execution.

### Stage 6: Visualization planning

Choose the appropriate widget types.

For example:

| Request | Visualization |
|---|---|
| Top 10 players | Leaderboard |
| Compare two players | Comparison |
| Runs by year | Line chart |
| Player statistics | Table |
| Live match | Scorecard |
| Explain a statistic | Text |
| Performance distribution | Histogram |

The planner can select multiple visualizations for complex requests.

### Stage 7: Validation and response

Validate:

- Widget schema.
- Data types.
- Metric definitions.
- Data provenance.
- Required fields.
- Widget interactions.
- Query result completeness.

Only validated specifications should reach the frontend.

## 5.3 LLM implementation

Use a hosted LLM through a provider abstraction.

The initial provider can be selected based on structured output support, tool calling, cost and latency.

The application should not be tightly coupled to a specific model vendor.

Define an interface such as:

- `interpret_prompt()`
- `resolve_entities()`
- `plan_query()`
- `plan_visualization()`
- `generate_explanation()`

Keep the model configuration externalized through environment variables.

## 5.4 Query DSL

Introduce a restricted analytical query language.

The LLM generates this DSL rather than unrestricted SQL.

Example:

```json
{
  "entity": "player",
  "dataset": "batting_performances",
  "filters": [
    {
      "field": "format",
      "operator": "equals",
      "value": "TEST"
    },
    {
      "field": "opposition",
      "operator": "equals",
      "value": "AUSTRALIA"
    }
  ],
  "metrics": [
    "runs",
    "batting_average",
    "strike_rate"
  ],
  "groupBy": ["player_id"],
  "orderBy": [
    {
      "field": "runs",
      "direction": "desc"
    }
  ]
}
```

The backend validates the DSL and translates it into parameterized database queries.

# 6. Cricket Data Architecture

## 6.1 Data-source strategy

Use multiple sources through provider adapters.

### Historical ball-by-ball data

Primary candidate: Cricsheet.

Use it for:

- Ball-by-ball analysis.
- Innings reconstruction.
- Batting and bowling statistics.
- Player matchups.
- Partnership analysis.
- Over-by-over performance.
- Advanced analytics.

Cricsheet data should be ingested into our own database.

### Historical statistics

Evaluate:

- Cricguru: https://github.com/puppetmaster12/cricguru
- Howstat: https://github.com/pranavrc/howstat
- ESPNcricinfo Statsguru.

These are experimental adapters, not core application dependencies.

Verify current repository implementation, dependencies, source-site restrictions, data coverage and licensing before adopting either library.

### Live scores

Evaluate a commercial or officially supported cricket data provider.

Provider selection must consider:

- Match coverage.
- Scorecard completeness.
- Update frequency.
- Delivery-level commentary availability.
- Historical scorecard access.
- Pricing.
- Terms of use.

Do not make undocumented endpoints or fragile scraping the permanent live-score infrastructure.

## 6.2 Provider abstraction

Create interfaces:

- `HistoricalDataProvider`
- `LiveScoreProvider`
- `FixtureProvider`
- `PlayerImageProvider`

All providers must return normalized application models.

A provider should never expose its raw response format directly to the frontend.

## 6.4 Statistical calculation engine

Implement deterministic cricket-specific calculation functions.

Examples:

**Batting average**

Runs scored divided by dismissals.

**Batting strike rate**

Runs scored divided by balls faced, multiplied by 100.

**Bowling economy**

Runs conceded divided by legal balls bowled, multiplied by six.

**Bowling average**

Runs conceded divided by wickets credited to the bowler.

**Bowling strike rate**

Legal balls bowled divided by wickets credited to the bowler.

These calculations must respect format-specific rules, exclusions, penalty runs, extras, retirements, run-outs and other relevant dismissal scenarios.

The engine must also distinguish innings-level statistics from career aggregates.

## 6.5 Data provenance

Every analytical response should retain:

- Data source.
- Source identifiers.
- Dataset coverage.
- Applied filters.
- Calculation definitions.
- Last ingestion time.
- Query execution timestamp.

If a query cannot be answered accurately because data is missing, the application should communicate the limitation instead of fabricating a result.

# 9. API Design

Use REST APIs with versioning.

## 9.1 Prompt endpoints

### POST /api/v1/prompts

Submit a new prompt.

Request:

```json
{
  "prompt": "Show the top 10 IPL run scorers",
  "action": "ADD",
  "targetWidgetId": null
}
```

For updating an existing widget:

```json
{
  "prompt": "Only include players with at least 50 matches",
  "action": "UPDATE",
  "targetWidgetId": "widget-123"
}
```

Response:

```json
{
  "executionId": "execution-123",
  "status": "COMPLETED",
  "widgets": []
}
```

For longer queries, the API may return an execution ID and a pending status. The frontend can receive completion through Server-Sent Events.

# 10. Database Architecture

## 10.1 PostgreSQL

PostgreSQL will hold canonical cricket data, metadata and normalized statistical records.

Use indexes for:

- Player IDs.
- Match IDs.
- Competition IDs.
- Match dates.
- Team IDs.
- Format.
- Venue IDs.
- Common analytical filters.

Partition the delivery table by match date or another suitable key only when the data volume justifies it.

Do not prematurely introduce complicated partitioning.

## 10.2 Raw data storage

Retain original downloaded datasets where practical.

Use compressed JSON files or Parquet for raw and intermediate analytical datasets.

This allows us to reprocess source data when our normalization logic improves.

## 10.3 Redis

Redis will be used for:

- Live score caching.
- Provider response caching.
- Expensive query caching.
- Background task coordination.
- Rate-limit coordination.

Redis should remain optional for local development where practical.

# 11. Live Cricket Architecture

Live data should be isolated from historical analytics.

## 11.1 Polling

Target update interval: approximately 60 seconds.

The backend should poll the provider rather than allowing every browser widget to independently call the external API.

## 11.2 Flow

1. Discover active matches.
2. Retrieve match status.
3. Fetch scorecard updates.
4. Normalize the response.
5. Update Redis cache.
6. Make updated information available to the frontend.
7. Refresh relevant widgets.

## 11.3 Scorecard structure

A live scorecard should support:

- Teams.
- Current innings.
- Score and wickets.
- Overs.
- Current run rate.
- Required run rate, when applicable.
- Target, when applicable.
- Batting players.
- Bowling players.
- Partnerships, when available.
- Recent overs.
- Fall of wickets.
- Previous innings.

Expanded scorecards should show detailed batting and bowling tables.

The interface should preserve the user's expanded or collapsed state across updates.

## 11.4 Provider failure

If a provider fails:

- Retain the last known score.
- Display its last update time.
- Mark the data as stale.
- Retry with controlled backoff.
- Do not present stale information as live.

# 12. Security and Reliability

Even though this is a local pet project, security should be part of the design.

Requirements:

1. Never execute arbitrary LLM-generated JavaScript or Python.
2. Never expose database credentials or LLM API keys to the browser.
3. Restrict LLM operations to approved tools.
4. Use parameterized SQL.
5. Validate all widget specifications.
6. Limit query execution time and result sizes.
7. Validate external image URLs and avoid unsafe content embedding.
8. Apply provider rate limits.
9. Keep logs free of API secrets.
10. Use Docker secrets or environment variables for local configuration.
11. Restrict external provider requests to configured destinations.
12. Avoid exposing the local application to public networks by default.

For reliability:

- Isolate widget failures.
- Add query timeouts.

# 19. Final Architecture Decisions

| Decision | Final choice |
|---|---|
| Product | Cricket Canvas |
| Architecture | Modular monolith |
| Frontend | React + TypeScript + Vite |
| Backend | Python + FastAPI |
| AI | Hosted LLM with provider abstraction |
| AI output | Structured query and widget specifications |
| Database | PostgreSQL |
| Cache | Redis |
| Analytics | Polars + Pandas |
| Historical data | Cricsheet + evaluated supplemental sources |
| Live data | Provider adapter |
| Visualization | Apache ECharts |
| Dashboard layout | React Grid Layout |
| Frontend state | Zustand + TanStack Query |
| Local persistence | IndexedDB |
| Deployment | Docker Compose |
| Authentication | None initially |
| Theme | Dark-first |
| Refresh interval | Approximately 60 seconds |

**Architecture principle:** The LLM interprets and plans. The backend validates and calculates. The frontend renders and manages the interactive workspace. Data providers supply the underlying facts.

This separation is the foundation of Cricket Canvas.
